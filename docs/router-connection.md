# Router connection plan

## What registration captures

The business onboarding form records:
- Router brand and model.
- Hotspot site and physical address.
- Router display name.
- Integration mode.
- Optional LAN management address and API port as setup references only.

No router password, API secret, or shared key is collected or written to the public database by this registration flow.

## Important network limitation

A router LAN address such as `192.168.88.1` is private and cannot be reached directly from a public Cloudflare Worker. A public router API port should not be exposed to the internet just to make the dashboard work.

## Secure pairing design to implement next

1. The authenticated business owner requests a one-time pairing challenge from EAM-WIFI.
2. EAM-WIFI issues a short-lived, single-use pairing token.
3. The router-side agent/script initiates an outbound HTTPS connection to the EAM-WIFI Worker.
4. The router proves possession of the pairing token and registers its device identity.
5. The system stores only the minimum device metadata and a revocable credential hash or encrypted secret in a restricted secret store.
6. Router events and heartbeats are sent over authenticated HTTPS; tokens can be rotated and revoked.

For MikroTik, the next implementation should use a RouterOS-compatible outbound script or a small local connector. Do not enable an unrestricted public RouterOS API port. Credentials must never be placed in browser JavaScript, GitHub, ordinary logs, or the general `network_devices.config` JSON field.

## Current implementation status

The registration RPC creates the organization, owner membership, hotspot site, router metadata record, and organization settings in one database transaction. It marks the organization as `pending` and the router as `not_configured`.

**Registration alone is not a live router connection.** The owner must complete the dashboard pairing and install the RouterOS connector before the router is online. The connector applies voucher user limits, but its behavior must be tested on the exact physical router and RouterOS release.


## Implemented connector foundation (November 2026)

- Owner/admin-only one-time device credential issuance at `POST /api/router/pair`.
- 256-bit random token generated by Cloudflare Worker Web Crypto; only SHA-256 hash stored in restricted `private.router_device_credentials`.
- Token activation window is 10 minutes; issuing a replacement revokes the previous active credential for that device.
- Router-initiated HTTPS heartbeat at `POST /api/router/heartbeat`; updates the registered MikroTik device's connected status and last-seen timestamp.
- RouterOS v7 heartbeat starter: `mikrotik/eam-wifi-heartbeat.rsc`.

This identity/heartbeat foundation is now extended by authenticated event polling and acknowledgement. The RouterOS connector template is stored in public/downloads/eam-wifi-agent.rsc; physical router behavior still requires device testing.


## Owner dashboard pairing and RouterOS connector

After the business subscription is active, the owner opens the business dashboard and selects Connect MikroTik router. EAM-WIFI creates a one-time 256-bit token with a 10-minute initial pairing window. The token is displayed once. Copy the commands shown by the dashboard and paste them into the MikroTik Terminal. The commands download and import the public connector script at /downloads/eam-wifi-agent.rsc.

The script is designed for RouterOS 7.13+ and:
- sends outbound HTTPS heartbeat to https://wifi.eckson.workers.dev/api/router/heartbeat;
- polls /api/router/events every 15 seconds;
- creates the Hotspot user/profile for voucher-redemption events;
- removes the Hotspot user for session-expiry events;
- acknowledges each event through /api/router/events/complete;
- never opens an inbound RouterOS API port.

Allow DNS and outbound TCP 443 from the router. Keep the pairing token on the router; do not paste it into support messages, screenshots or GitHub. After successful first pairing the database renews the device credential for one year. A fresh pairing can rotate/revoke a credential.

The connector is a RouterOS script template, not a claim that every RouterOS version or Hotspot configuration has been tested. Test on the exact router model/RouterOS release, validate the Hotspot login page and walled garden, and inspect EAM-WIFI router status before serving paying customers. MikroTik Hotspot is the first supported integration; arbitrary router brands are not remotely provisioned yet.

## Operational verification checklist

1. Confirm the router appears Online in the business dashboard after pairing.
2. Confirm the router event queue is empty after test events are acknowledged.
3. Create a low-value test package and issue a test voucher after recording test payment.
4. Redeem from a phone on the hotspot; confirm automatic router login and internet access.
5. Confirm /ip hotspot user print shows the EAM-WIFI user with expected uptime/data/profile limits.
6. Test duplicate redemption, wrong code, wrong business, disabled package, expired voucher and offline router; all must be rejected.
7. Test connected-time exhaustion, data-cap exhaustion and wall-clock expiry. Confirm the active user is disconnected/removed and the database session reaches expected status.
8. Repeat after router reboot and temporary internet outage. Do not declare production-ready until these tests pass.
